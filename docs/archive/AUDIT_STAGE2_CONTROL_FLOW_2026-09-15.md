## 范围与结论

检查当前工作区的配置 → 控制器读盘 → 决策 → 执行 → 恢复及结果汇总链路。本次只分析，不修改生产代码。工作区已有未提交修改，且审计期间源文件有外部更新；以下位置按本轮最后核对的代码记录。

核心问题是跨层契约没有闭合：同一配置没有到达每条腿；同一个生产块在准入和执行时大小不同；被判为零采样成本的动作实际会采样。单独修复某个决策分支不能解决这些问题。

## 1. 溶剂腿控制器丢失运行配置（P1）

- 写侧：`runabfe.py` 的 `_write_run_provenance` 把配置写入总输出目录的 `run_provenance.json`，主流程调用位于约 7040 行。
- 溶剂腿：约 7515–7529 行将其输出及检查点放入 `output_dir/solvent_leg`。
- 读侧：`abfe_preoptimizer.py` 的 `Stage2RepairController.__init__` 只读自身 `run_dir/run_provenance.json`（约 2531 行）。`abfe_pipeline.py` 约 11147 行创建控制器时仅显式传入窗口上下限和 untrusted 开关，没有传完整有效配置。

**复现：** 按真实主流程的目录结构，在总目录写入配置，子目录不额外复制 provenance；通过 AST 提取并执行当前源码中的真实 `__init__` / `_json`，结果如下。

| 字段 | 复合物腿读取值 | 溶剂腿读取值 |
|---|---:|---:|
| 分窗判据 | metric_integral | arclength |
| 每块生产步数 | 500000 | 250000 |
| 生产总预算 | 2000000 | 未知 |
| 插点次数上限 | 8 | 3 |
| 每窗块数上限 | 7 | 4 |

**后果：** 同一运行的两条腿使用不同的预算和修复策略。溶剂腿的明确预算可能失效；修复分窗判据可能偏离生产判据；插点和块数可能提前受限。

**修复方向：** 将解析后的有效控制配置显式传入控制器；离线 replay 使用同一份配置快照。不要依靠各输出子目录偶然存在一份配置文件。

## 2. 自治执行块恒取 250000 步（P1）

`ABFEPipeline.run_full_pipeline` 在 `abfe_pipeline.py:14178` 将 `n_steps_per_window` 声明为正式参数。调用 `_run_stage2_autonomous` 时，约 16316–16317 行却使用 `int(kwargs.get("n_steps_per_window", 250_000))`。正式参数已被 Python 参数绑定取走，因此不会留在 `kwargs`，函数内也未将其回填。

**复现：** AST 提取当前调用点的参数表达式并执行：配置为 50000、250000、500000 时，自治循环收到的值都为 250000。

**后果：** 首轮采样使用真实参数（约 16171 行），控制器预算从 provenance 读取真实参数，而自治补采及子窗执行使用 `base_unit=250000`。例如配置 50000 时，按 50000 准入的动作可能实际追加 250000；配置 500000 时则可能按 500000 拒绝一个实际只会执行 250000 的动作。

**修复方向：** 直接传递正式参数，并使动作计划明确包含目标步数、预计增量及预计成本；执行器按计划执行，不再另取默认值。

## 3. 结构动作绕过生产预算后直接采样（P1）

`Stage2RepairController.decide` 的 `plan()` 在 `abfe_preoptimizer.py:4184–4193` 把 `INSERT_LAMBDA` / `SPLIT_TAIL_WINDOW` 排除在生产成本检查之外，理由是它们仅改变布局，采样留到下一轮 `RUN_PRODUCTION`。

实际执行器在 `abfe_pipeline.py:11682` 和 `11736` 改完布局后立刻调用 `run_once(...)`，没有指定窗口子集，也没有在新布局下重新进行生产成本准入。`run_once` 接入 `_run_dual_lambda_stage`，会对缓存失效或缺失的窗口执行采样。

**触发：** 控制器选择插点或尾段重分，且受影响窗口需要重采；即使生产预算不足，结构动作本身也不触发生产准入检查。

**后果：** 一个动作可能启动多个受影响窗口的重采，直到之后读盘才发现超支；“每个动作之后重新判断”的调度边界也被扩大为一次整段采样。

**修复方向：** 二选一并统一实现：结构动作只提交新布局，下一轮逐块准入采样；或者计划提前列出所有受影响采样单元，预留完整成本后再执行。不能在决策层称零成本、执行层直接采样。

## 验证边界

- 已执行两项纯 Python 源码片段复现（配置读取、调用参数绑定）。
- 结构动作问题已核对决策分支与真实调用链，未运行 GPU 采样。
- 当前本机可用 Python 缺少 OpenMM、pytest、SciPy，未声称完整回归测试通过。
- 旧数值质量阈值在当前设计中已改为报告项，因此“不因旧阈值失败而抛错”本身不列为缺陷。

## 后续验收应覆盖的完整序列

1. 总目录与溶剂腿使用同一显式配置，验证两者解析出的预算及分窗判据一致。
2. 非默认块大小下，计划成本、实际追加步数、落盘预算三者一致。
3. 剩余预算小于重采成本时，插点／拆窗不能越过采样准入。
4. 每次执行后重建控制器，验证恢复后的下一动作与连续运行一致。

这些应是行为测试，不能只断言源码中出现了某个参数名或分支字符串。
