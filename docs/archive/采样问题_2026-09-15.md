## 问题

```

 └─ 换 Epoch 付不起验证额度
     └─ 降级发 RUN_PRODUCTION（复用冻结 f_k，不花预热预算）
         └─ 没有任何预算量能判定它不可行 ⟹ 恒"可行"
             └─ 连补至 max_production_blocks=4
                 └─ NO_FEASIBLE_ACTION，窗口仍未达标
```

`abfe_preoptimizer.py:4918` 注释自己写明了：

> 「新 Epoch 付不起验证额度 ⟹ 退而补生产帧」…… `RUN_PRODUCTION` 用的是**已冻结的 f_k**，


# 采样问题（二）：对"偏斜"发"补帧"，且失败窗口被 earliest 排序挡在队尾

2026-09-15 · 证据来自 `abfe-benchmark/openmm_IBS/runs/brd4_ligand1/rep2`，零 GPU 重算
（这是上一节那条链的**下游**：上一节问"为什么只补帧不重标定"，本节问"为什么补给了
错的窗口、以及为什么真正该修的窗口一次都没轮到"）

## 现场

自治循环 6 轮，`stage2_autonomous_history.json`：

```
轮1   PROBE_CANDIDATE_FK [1]
轮2-5 RUN_PRODUCTION     [1]        ← 四块帧，把 max_production_blocks=4 烧光
```

## 问题①：对"偏斜"发了"补帧"

win1 `n_decorr=888`（门 10，够得离谱）、`min N_eff/g=8.68`。**它不缺帧，它偏斜。**
自检自己把这句印在日志里：

> 「不是帧数不够（去相关下限已达标）——差的是目标态的有效样本 min N_eff/g。
> **同分布加帧治不了偏斜**：对症动作是换 f_k 或缩窗跨度（插 λ），不是更多帧。」

而控制器连发四块 `RUN_PRODUCTION`，直到配额打满才停。

判据量**早就都在自检产物里**（`verdict_source` ∈ `solver_eligibility` /
`min_n_eff_over_g` / `top1pct_veto`），不需要新发明。分流应当是：

| verdict_source | 含义 | 对症动作 |
|---|---|---|
| `solver_eligibility` | 真缺帧（`n_decorr` 不够） | `RUN_PRODUCTION` |
| `min_n_eff_over_g` | 帧够但偏斜 | 换 f_k / `INSERT_LAMBDA` 缩跨度 |
| `top1pct_veto` | 单帧支配 | 同上，且**明确禁止**同分布加帧 |

⚠️ 这条分流**代码里已经有**，但只挂在 rewindow 子窗上，物理窗口这条路没挂：

> `abfe_preoptimizer.py` 分支 1c 注释：「[CTL-02] **只有"缺帧"才走补帧这条分支。**
> 支撑/偏斜类失败的子窗由下面的 1c-2 单独处理 —— 拿加帧顶替它正是要修的那个错。」

## 问题②：earliest 排序让 win4 一次都没被看过

控制器只路由 `earliest` 未解决窗口，其余进 `blocked_by_upstream`。于是：

```
win1 偏斜 ⟹ 加帧治不好 ⟹ 永远"未解决"
     ⟹ win4 永远轮不到
         ⟹ 那个 HARD_INSUFFICIENT + top1%=0.45、真正需要插 λ 的窗口，从头到尾没被看过一眼
```

预算全花在一个**结构上加帧治不好**的窗口上，跑完再让全队陪葬。

一个加帧治不好的窗口不该无限期挡住后面所有窗口——它自己该先走布局动作。
（`earliest` 的原意是"前缀不合格就别跑下游"，那对**缺帧**成立，对**偏斜**不成立：
偏斜窗口的对症动作是布局类，而布局动作本来就会重排下游。）

# 采样问题（三）：隔壁三条的核实结果 + 误差的真实形状（2026-09-15，零 GPU）

## 隔壁报的三条

| | 结论 |
|---|---|
| ① 采样问题解释 cyclod 的 1.4–1.6 kcal 散布，解释不了 brd4 的齐整系统项 | ✅ 同意 |
| ② `max_blocks_per_window = max(1, int(None))` 硬崩 | ✅ **已修**，但归因要更正 |
| ③ 溶剂腿 vdW 系统项嫌疑在 `legacy_uniform_density_lrc` | ❌ **排除** |

### ② 归因更正

**代码是有默认值的**（`_cfg.get("stage2_max_production_blocks_per_window", 4)`）。
崩是因为 2026-09-15 当天为审计 #1 加 `effective_config` 时往里塞了显式 `None` ——
`{"k": None}.get("k", 4)` 返回 **None 不是 4**。默认值防不住一个"存在的 None"。
已改：值为 None 的键**整个不放进** `effective_config`，且改成三层合并
（显式 > provenance > 默认），免得只传部分键把复合物腿打回默认值。

### ③ 排除的依据（从落盘 XML 离线复算，零 GPU）

    complex  N_lig=56  N_env=39633  V=416.9  ρ_env=95.07  coeff=−5543.60  E_LRC=−13.2983 kJ/mol
    solvent  N_lig=56  N_env= 5914  V= 62.3  ρ_env=94.87  coeff= −792.14  E_LRC=−12.7079 kJ/mol

    两腿差 = −0.5904 kJ/mol  ÷ 56 个有 LJ 的配体原子 = −0.0105 kJ/mol/原子
    目标                                              = −1.85  kJ/mol/原子   ⟹ 差 176 倍

**机制也不对。** `coeff` 是对「配体 × 环境全部原子对」求和 ⟹ `coeff ∝ N_env` ⟹
`E = coeff/V ∝ N_env/V = 环境数密度`。两个盒子的 ρ_env 只差 0.2%（95.07 vs 94.87），
**6.7 倍体积差被彻底抵消**。「两条腿盒子差 4.5–6.7 倍体积」不是这条的机制。

### 顺带排除：配体内部处理

两腿 `system_native.xml` / `system_solvent.xml` 逐位比对：
