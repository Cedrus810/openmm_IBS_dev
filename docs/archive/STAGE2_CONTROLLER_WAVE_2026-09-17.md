## 3. 缺口（**一条都没修**）

### A. solver 侧证据在整个采样阶段是空的

`_read_stage_result()` 恒 `None` —— stage 结果**只在 `ANALYZE` 执行时**落盘，
而 `ANALYZE`（分支 8）排在补帧那一族之后，只要还有窗口缺帧就永远轮不到。

**三条判据的输入全空，而且全部静默"通过"**：

| 判据 | 输入 | 实际 |
|---|---|---|
| 补帧边际增益刹车 | `solver_n_frames_decorrelated` | 全窗 `None` → 判据量 `[None,None,None]` → `marginal_gain_stalled()` 过滤后空列表 → 恒 `NOT_ENOUGH_POINTS` → **永不触发** |
| 累计 f_k 偏差链（5a-1/5a-2） | `cum_fk_verdict` | 全 `None` → **永不进入** |
| 跳窗路由（1d / 6） | solver 侧 `skipped_windows` | 恒空 → **永不触发** |

**实测**：`cyclod_ligand2/rep1` w5 连批 3 块、`cmet_ligand1/rep2` w0 连批 3 块、
`cmet_ligand2` 那次崩溃的 w4 批满 4 块 —— 判据量全程 `None`。

剩下的保护是**块数硬上限（4）+ 射程闸**，这两道是活的，所以不会无限烧；
但「加了一块没带来增益就停」这条规则在实际运行中**等于不存在**
（w4 的 4 块是被"块数上限"停的，不是被"没增益"停的）。

**附带**：诊断词 `NOT_ENOUGH_POINTS` 误导 —— 读起来像「才跑了 1-2 块」，
实际是「这个判据一个输入都没有」。两者处置完全不同。

### B. 缺窗覆盖被**纯补帧**挡住

```
cmet_ligand1/rep2：布局 5 窗，产物 3 个 ⟹ missing=[3,4] 从没采过
  w0  850k 步  ratio=8.88  已吃 3/4 块   ← 全部预算在这
  w2  还在 WARMUP_VALIDATE，一起被挡
```

缺窗分支（6b）**故意**排在因果顺序之后，理由是「上游**重锚**会作废下游 warmup lineage」。
但 w0 拿到的是 `RUN_PRODUCTION` —— 同一份冻结 f_k、接着原段，**不重锚、不改布局、
作废不了任何下游**。用它挡住两个从没采过的窗口**没有物理依据**。

### E. 插 λ 对**末窗**是空动作，且边际停滞分支不考虑拆窗

失败窗口 == 末窗时，model B 的「溢出落末窗」落回它**自己**：

```
cmet_ligand2/rep1（执行器自己打的）：
  [自治] 插 λ：窗口 (16, 21) 跨度 0.2247 → 0.2247；末窗吸收溢出。
  [自治] 插 λ：窗口 (16, 22) 跨度 0.2247 → 0.2247；末窗吸收溢出。
  ranges: (16,21) → (16,22) → (16,23)      K: 5 → 6 → 7
```

这条动作的全部理由是「瓶颈是**跨度** ⟹ 对症动作是**缩小跨度**」。
末窗上它做不到，**而执行器已经把 `0.2247 → 0.2247` 打在日志里，零处消费**。

而且当时**拆窗是可行的**（`feasible: split_tail_window=None`，`anchor=0.22465573`），
拆窗会真的缩跨度。但命中的是**边际增益停滞**那条分支，它的动作写死成 `INSERT_LAMBDA`，
**从头到尾不考虑 `SPLIT_TAIL_WINDOW`**，而它排在会比较两者的 5b **之前**。

代价：插点终身预算 3 次用掉 2 次，两次跨度都没变，每次附带窗口全量重采。
`no-op` 台账抓不到它 —— 插 λ 推进了 `path_version`，指纹随之改变。

> ⚠️ **非末窗的插 λ 是有效的**：同一个 run 实测 `0.4067 → 0.3810 → 0.3532`、
> `0.2670 → 0.2473`。E 只对**失败窗口恰好是末窗**的情形成立。

### F. 布局动作**没有任何事后有效性检查**

补帧那条路有刹车（`marginal_gain_stalled`）。插 λ / 拆窗这条路**一个都没有**。

```
cyclod_ligand1_outer/rep1  窗口 1：
  插 λ 前   跨度 0.2670   ratio 2.32
  插 λ 后   跨度 0.2473(−7.4%)   ratio 1.14   ← 掉了一半
  补一块后  跨度 0.2473   ratio 1.26
  下一步    再插一次
另一窗口更早两次连插：0.4067 → 0.3810 → 0.3532，每次只缩 6~7%
```

用 6% 的跨度去救一个离门 8 倍的比值，算术上就不成立，**没有任何判据会这么说**。

**两笔没人算的附带代价**：

1. **每次插 λ 把增益历史清零** —— `min_n_eff_over_g_history` 按 `path_version` 过滤，
   版本一推进历史重启 ⟹ 补帧那道唯一活着的刹车也跟着失明；
2. **每次插 λ 作废下游窗口的证据** —— 该 run 的 w4 现在是 `stale_layout_evidence_only=True`，
   必须重采。

⟹ 一次"缩跨度"的真实成本 = **目标窗口重采 + 下游重采 + 增益历史清零**，
收益是跨度 −7%。没有任何地方把这笔账摆出来。

### H. 「总是改变盘面」的动作对停滞保护与 no-op 台账**结构性免疫**

停滞保护的定义是「**同一个动作 + 盘面未变**」（`seen[key] >= 3`）。
而 `RECALIBRATE_FK` **按构造必然改盘面** —— 它 `probe_only=False`、**开一个新采样段**，
`_disk_signature()` 里的 `segment` / `aggregated_segments` 随之改变
⟹ `seen[key]` 每轮重置成 1 ⟹ **永远到不了 3**。
`no-op` 台账同理：`action_noop_fingerprint()` 含段维度（`segment` /
`n_production_segments`），新段 = 新指纹 ⟹ 记录永不匹配。

⟹ **这一族动作对唯一的通用刹车免疫。** 再叠加 §3.F（布局/Epoch 动作没有事后
有效性检查），就可以无限重标定，而且**每次丢弃上一段的累计生产步数**。

**真机 `cmet_ligand1/rep1`（31/40 轮里 17 轮花在窗口 4）**：

```
 20 RECALIBRATE_FK  seg=vanishing    steps=750000  ratio=9.645   ← 离门 10 只差 0.355
 21 RECALIBRATE_FK  seg=vanishing_4  steps=250000  ratio=4.182   ← 新段，750k 步作废
 22 RECALIBRATE_FK  seg=vanishing_5  steps=250000  ratio=0.837   ← 又一新段
 23 RECALIBRATE_FK  seg=vanishing_6  steps=250000  ratio=7.017   ← 又一新段
 24 INSERT_LAMBDA   seg=vanishing_6  steps=250000  ratio=7.017
 28 INSERT_LAMBDA   seg=vanishing    steps=500000  ratio=3.766   ← 插完 7.45→3.77（§3.F 又一例）
```

它在第 20 轮时**再补一块几乎必过**；三次重标定把它推到 0.837，全程无人察觉。
盘上留下 7 个采样段（`vanishing` ~ `vanishing_7`），每个都是一整段 GPU。

⚠️ **这条与 §3.F 是两件事**：F 是「没有事后判定」，H 是「**连"重复"都检测不到**」。
只修 F 不修 H，控制器仍然可以每轮换一个新段来绕过重复计数；
只修 H 不修 F，第 3 次会被拦下，但前两次仍然白烧。

⚠️ 别用「把 `RECALIBRATE_FK` 加进 `_NOOP_GUARDED`」来补：no-op 判据问的是
"盘面变没变"，而它**真的变了**（新段是真实产物）。要判的是"变好还是变坏"，
那是 §3.F 的判据，不是 no-op 的。

### I. 末窗被推到 `K == hi` 就卡死：既不拆，也再插不进

拆窗的触发条件是 `abfe_pipeline.py:11429`：

```python
if _tk > int(max_states_per_window):      # 8 > 8 → False
```

**只在 K 超过 `hi` 之后才拆** —— 也就是**布局已经非法了**才补救。
K 恰好等于 `hi` 时（默认 4/8 配置下就是 K=8）：

- **不会拆**：`8 > 8` 为 False；
- 它是**全路径最宽的窗口**，而且是**末窗**（最难的那个）；
- **插 λ 同时关死**：`feasible()` 判 `K_after = 9 > hi = 8`，取不到 tail anchor
  就判不可行（见该函数里「anchor 缺口」那段）。

⟹ 末窗停在最差的形态上，**两个缩跨度动作一个都用不了**。

**每一步把它推到这里的代价，日志自己写着**（真机 `[窗口 5] 索引 [16:24] | 状态数: 8`）：

```
[WARN] 窗口 5 缓存能量形状 (5, 500) 与期望 (8, N) 不符，将重新采样该窗口。
[WARN] IBS 状态与当前窗口不兼容 (cache n_states=5, current=8)，忽略旧状态
```

窗口 5 从 5 态被插到 8 态，**每插一次**：① 整窗能量缓存作废 → 全量重采；
② **学好的 f_k 被丢弃**（`忽略旧状态`）→ 从头重学。而按 §3.E，
**失败窗口恰好是末窗时插 λ 根本不缩跨度**（`0.2247 → 0.2247`）。整条链是：

```
末窗失败 → 插 λ（跨度不变）→ 末窗变宽 → 能量 + f_k 全废 → 重采 + 重学
        → 还是失败 → 再插 → … → K 撞到 hi → 插不动了、也不拆
```

**每一轮都更贵、更宽、更难，而判据认为"我在缩跨度"。**

⚠️ **别把触发条件简单改成 `>=`**：`_legalize_tail_window` 的死区讨论
（`K ∈ (hi, 2·lo−1)` 既当不了单窗又拆不开）说明这里的区间关系是刻意设计的；
K == hi 是**合法**的单窗，问题不在"它非法"，而在"它是最差形态且没有出路"。
正解要回答的是：**末窗涨到什么程度就该主动拆**（而不是等它非法），
以及 §3.E 那条「失败窗口是末窗时插 λ 不该被选中」。两条要一起看。

### J. **model B 的收尾动作「末窗一分为二」在自治控制器下整个不存在** ← E 与 I 的共同根因

原始设计写在代码里（`abfe_preoptimizer.py:9556`，`feasible_repair_actions` 内）：

```
# ---- 拆**末窗本身**：两子窗共享一个边界态 ⟹ p + q − 1 = K，两侧都落在 [lo, hi] ----
# 这一条问的是「溢出槽长到能一分为二了没有」，是 model B 插点的收尾条件。
...
"继续插 λ 让末窗长大即可到达；拆窗只是末窗溢出压不住时的收尾动作。"
```

即：**插 λ 把末窗（溢出槽）养大，到 `K ≥ 2·lo−1`（lo=4 时 K=7）就一分为二。**

**三样东西齐了两样，唯独接线断了**：

| | 状态 |
|---|---|
| 判据 `split_last_window_in_two` | ✅ 每轮都算，两个真机盘面都答**可拆**（`None`） |
| 执行器 `split_window_from_ibs_lse_failure`（末窗一分为二） | ✅ 存在（`abfe_preoptimizer.py:1497`） |
| **调用者** | ❌ **全仓只有一个**：`abfe_pipeline.py:10933`，在 `path_evolution` 的异常处理里 |

而自治控制器**显式关闭**那条路径 —— 每份日志都印着：

```
[控制器] 自治控制器已启用 ⟹ 关闭 rescue 后 f_k 重标定、
         path_evolution 的插 λ 修复分支（已降级为 non_mutating_v1）、bridge rescue
```

代码里还有断言钉死（`abfe_pipeline.py:17169`）：
`assert _sampling_repair_policy != "path_evolution_v1"，"自治控制器启用时不得并存"`。

⟹ **`split_last_window_in_two` 这个可行性每一轮都在算、答案是"可拆"，而全仓没有任何
一处在自治模式下消费它。判据活着、执行器活着、动作不存在。**

控制器自己的 `SPLIT_TAIL_WINDOW` 是**另一个更重的动作**
（`repartition_tail_from_anchor`：从 anchor 起重分**整个尾段**，需要 tail anchor），
不是「末窗一分为二」。2026-09-14 的审计 #24 把这两个问题分开时，
判据留在了 `split_last_window_in_two`，**但没给控制器补上对应的动作**
（#24 自己的注释只讨论了"不拿末窗那条冒充 SPLIT_TAIL_WINDOW"，没讨论"那谁来做末窗那条"）。

**⟹ §3.E 与 §3.I 不是两个独立缺陷，是同一个缺失的两个症状**：

```
末窗失败 → 插 λ（§3.E：跨度不变，因为溢出落回它自己）
        → 末窗变宽、能量缓存 + 学好的 f_k 全废 → 重采 + 重学
        → 还是失败 → 再插 → K 撞到 hi（§3.I：不拆、也插不动了）
```

**中间本该有一步「K ≥ 2·lo−1 就一分为二」，判据和执行器都在，只是没人叫它。**

⚠️ 修它**不是**重新打开 `path_evolution`（那条被关是有理由的：同一个决定不许两套机制
各判一次）。要做的是把「末窗一分为二」作为**控制器的一个动作**补进动作表 + 执行器分发，
判据直接用现成的 `split_last_window_in_two`。这条一补，E 和 I 自动消解。

### K. `ANALYZE` 在有过期证据的盘面上炸穿流水线（判据侧知道、执行器侧不看）

```
[自治] 执行 ANALYZE 失败：ValueError('窗口 4 lambda 内容与当前路径不匹配')
_solve_merged_segments_if_any → _load_ibs_window_outputs_merged
  → ibs_engine.load_ibs_window_outputs_from_dir:664 → raise ValueError → 炸穿主循环
```

控制器**对补帧类动作有这道闸**（分支 1d-0、停滞降级的 `_stale_for_escalation`），
理由原文：「拿已有帧重解的动作在构造上都会维度不符，真机实测是直接 `ValueError`
炸出流水线」。**但 `ANALYZE` 没有这道闸** —— 而它恰恰是**跨全部段、拿已有帧重解**
的那个动作。

**判据侧其实完全知道**：`classify_layout_evidence()` 逐 (段, 窗口) 比 λ 身份，
`read_aggregated()` 把过期的排除出 `merged`、记进 `stale_layout_evidence`；
而 `_solve_merged_segments_if_any` 从盘上**无过滤**加载所有段。
⟹ **同一个不变量两份实现**，形态是"判据侧过滤了、执行器侧没过滤"。

真机盘面：`vanishing_2` 段只有窗口 4（逐段缺窗 `[0,1,2,3,5,6]`），
而它的 λ 与当前路径已不匹配（布局后来演化过）。

### L. 补帧的**块数硬上限**被「换布局」重置 ⟹ 补帧实际没有有效上限

`_production_blocks_total_by_window()`（**硬上限**）与 `_production_blocks_ledger()`
（**边际增益**）都把 `path_version` 传给 `_production_blocks_scan()`，而那里有
`path_version != it.path_version: continue` ⟹ **插一次 λ / 拆一次窗，补帧配额就清零、
重新发满 4 块**。

这与 `BUD-03` 是**同一个 bug 换了一个维度**（那次修的是「换**段**退钱」），
而本函数的定义白纸黑字写着「硬上限 = **资源账**，跨段累计」——
烧掉的 GPU 不会因为布局变了就回来。

**真机（修复后才看得见真实消耗）**：

```
cmet_ligand1/rep1  w4：旧口径 2 块  →  真实 9 块   （上限 4）
cmet_ligand2/rep1  w5：旧口径 4 块  →  真实 5 块
brd4_ligand1/rep2  w3：累计 1,250,000 步 = 5 块
```

叠加 §3.A（边际增益刹车全程没有输入、恒不触发）⟹ **在布局反复演化的 run 上，
补帧没有任何有效上限**。这正是跨 run 统计里最准那条判据的机制：
「至少一个窗口累计 ≥500k 步」覆盖 **9/9** 失败（`maxK≥6` 只覆盖 7/9）。

**已修**：硬上限那本**不按 `path_version` 过滤**；边际增益那本**仍然要过滤** ——
跨布局比 `min N_eff/g` 没有意义（窗口几何都变了），那是判据的**可比性**要求，
不是资源账。两者过滤维度不同，正是 BUD-03 把它们拆成两个函数的理由。

⚠️ 它的回归测试 fixture 必须用**单调递增**的 `production_steps`：块账按步数去重，
每个布局都从 250k 重来会被折叠掉，测不到要测的东西（我第一版就踩了）。

### M. 「布局过期 + 冻结验证批次打满」= 死锁 ⟹ 整跑终止

```
窗口过期（λ 不匹配）⟹ 分支 1d-0 判「只能重采」⟹ RUN_PRODUCTION
  → 重采要**重新进入**窗口 → 预热门看到 15/15 批打满
  → 抛 LOCAL_VALIDATION_CAP 弹回，盘面未变
  → no-op 还记不下（stale 窗口 production_steps 读不到 ⟹ 指纹没有可比身份，
     2026-09-15 那条保护刻意不落账）
  → 连发 3 次 → 停滞保护 → 降级又被 `_stale_for_escalation` 挡住
  → NO_FEASIBLE_ACTION，整跑终止
```

根因：**1d-0 排在 1e（进不进得去）之前，且无条件发 `RUN_PRODUCTION`**。
而对「验证批次打满」控制器**有**答案 —— 分支 3a 的 `PROVISIONAL_PRODUCTION`
（显式授权用未验证的冻结 f_k 采一个诊断块），只是排在后面够不着。
它产出的是**新布局下**的帧，所以**一并解决了证据过期**；普通 `RUN_PRODUCTION`
则在预热门上被弹回、一帧都产不出来。

**已修**：1d-0 分流 —— 过期**且**正卡在验证批次上限 ⟹ `PROVISIONAL_PRODUCTION`。
语义 / 额度（只给一个块）/ 证据口径（f_k 仍 `indeterminate`，**不是**可信 PASS）
全部照 3a 那套，判据复用**同一份** `local_validation_cap_hits()`，不在这里另写。

## 5. 并发协作记录

当天两个会话同时改同一棵树，付出过两次真实代价，规矩记在这里：

1. **并发写会让全量结果不可信。** 一次 15 red 的全量是被跑测途中的写盘造成的
   （`abfe_pipeline.py` mtime 落在跑测区间内，源码探针类用例读到半截文件）；
   单独重跑同组 41 passed。
2. **约定**：要跑全量的一方先说一声、跑完发数字；对方在那 3~4 分钟内不写
   `abfe_preoptimizer.py` / `abfe_pipeline.py` / `tests/`；落盘完主动说一句。
3. **一次真实逻辑冲突**（③″）：射程闸与归因各自回答"该不该给这个窗口帧"，
   用的量不同、都接在准入路径上。**一个人写也会撞** —— 这是本仓的签名形状
   （同一个决定两套判据），不是协作问题。
4. **互相复核比各自加守卫值钱**：③′ 是对方的改动、由我复现盘面找出；
   ②的半截（补了键、调用点没传参）是用户指出的；
   E/F/G 三条是拿真机盘面逐个跑控制器跑出来的，不是读代码读出来的。
